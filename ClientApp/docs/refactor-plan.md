## 1. What we are NOT doing, and why

**Not: "move each area out of ShapeManager into its own service, switch Frogmarks to the services, delete the
pass-throughs."** (Proposed by another AI.) Reasons:

1. It contradicts Salsa's recorded decision (audit A1/A2).
2. The "services" already exist — they're Salsa's sub-managers. Having Frogmarks call them directly means Frogmarks
   couples to a dozen engine internals instead of one stable API. Every internal Salsa refactor would then become a
   Frogmarks break.
3. ShapeManager isn't only Frogmarks' API: ~20 Salsa files use it (`main.ts`, packaging, the AI scene-authoring API).
   Deleting pass-throughs breaks those too.
4. It moves risk without removing complexity: the methods still exist, just in more places.

**Not: a big-bang rewrite of either file.** Each step below is small, verifiable, and independently shippable.

## 2. The plan

Ownership rule (from the user, 2026-10-02): Frogmarks' Claude may edit **only** Salsa's `shape-manager.ts`; any
other Salsa file goes to Salsa's AI first. Salsa's AI edits `shape-manager.ts` constantly, so every edit there is
small, surgical, and preceded by a `git diff` check of the file.

### Phase 1 — Finish the type safety net (audit T6) · Frogmarks · **do first**

The breakage protection a façade gives only works when the compiler sees the calls. Without it, a renamed Salsa
method fails silently at runtime — which is how the CD-kit delete button, the wind-zone panel, the 3D texture
save/restore and ~20 other features were silently broken until 2026-09-28.

| Step | What | Status |
|---|---|---|
| 1.1 | Remove `(shapeManager as any)` casts in `illustration.component.ts` (630) | ✅ 2026-09-28 |
| 1.2 | Delete the `(ShapeManager as any).getInstance?.(possibleRenderer)` call in `afterRendererBoot` — it passes a renderer where `getInstance` expects a shape factory and only works because the argument is ignored | ✅ |
| 1.3 | Drop `?.` from calls to methods that **exist** (`sm.foo?.()` → `sm.foo()`). Keep the leading `?.` where `shapeManager` itself can be unset (before boot). Turns future breaks from silent no-ops into loud errors. ⚠ Needs `tsc --strictNullChecks` filtered to TS2721–2723 to verify (project isn't strict) | ✅ editor (1,012) |
| 1.4 | Same burn-down for the other components/services | ✅ all 16 files; guard allowlist empty |
| 1.5 | Tighten the ~230 **argument-level** `as any` casts (host passes a loose `string` where the engine wants a union like `RenderStyle`) — fix the host types instead of casting | ⬜ |
| 1.6 | Regression guard script (no ESLint here) | ✅ `prebuild` |

**Verify after each step:** `npx tsc --noEmit -p tsconfig.app.json` = 0 errors, then `ng build` (the only thing that
type-checks the HTML templates). 1.3 changes no behavior except where a method didn't exist — and the compiler
proves none don't.

Extract one area at a time into a **child component** (its template chunk + its state + its methods), with the
parent passing `shapeManager` and any shared state in as `@Input`s and receiving events via `@Output`s. Pure logic
that several areas share (colour conversion, `_hexToRgba01` and friends) goes to a small `color-utils.ts` first.

Order — most isolated and smallest first, so the pattern gets proven on low-risk code:

## 3. Known cross-cutting issue to fix during Phase 2.8

Frogmarks keeps its own snapshot of the 3D scene settings (post-processing, film, fog, grid…) and re-applies it on
load, duplicating what Salsa already persists. In cloud mode the Frogmarks copy is applied **after** Salsa's, so a
stale Frogmarks copy wins. Resolution: one owner per setting — **Salsa** for everything it persists; Frogmarks only
for data Salsa doesn't store (e.g. the vending can-design source PNGs, which Salsa keeps only as a packed sheet).

## 4. How we know nothing broke

| Check | Catches | When |
|---|---|---|
| `npx tsc --noEmit -p tsconfig.app.json` (Frogmarks) | Wrong/renamed engine calls, type mismatches | Every step |
| `ng build --configuration development` (Frogmarks) | Template errors (bindings, missing members) — `tsc` does NOT check HTML | Every step |
| `npm run build` + `npx tsc --noEmit` + `npx vitest run` (Salsa) | Façade edits breaking Salsa | Every `shape-manager.ts` edit |
| Phase-1 guard script | New `as any` on the manager | Every build (once 1.6 lands) |
| Manual area checklist (below) | Behavior regressions — there are no real unit tests in Frogmarks (21 generated spec stubs) | After each Phase-2 extraction |

### Manual checklists per Phase-2 area (run in the browser)

- **GARP:** open Skins; add a variant; add/reorder/remove can designs; regenerate city; reload → designs still listed.
- **Packaging/CD:** create a package and a CD kit; open/close the designer; upload art; delete a kit from the outliner.
- **UI system:** create a layer + 2 states; bind a shape visible/hidden per state; preview + jump states; wire a
  button; reload → bindings persist.
- **World/creators:** generate a city; add + edit building / foliage / block / creator; Save to Library; delete.
- **Characters:** create; drag body sliders on an existing character; hair/clothing/eyes/charms; skin shading; joints;
  export/import preset; reload.
- **Render look:** outline + rings + boil + sprite shape; textures + tiling + triplanar; post incl. film; reload.
- **Armature/anim:** pose, record, play, play-with-idle, NLA; cloth + wind zones.
- **Persistence:** local + cloud: draw → reload; import `.frogmarks`; doc A → doc B switch; save-paused banner.
- **Outliner/inspector:** select/rename/hide/delete/duplicate/group; transforms show real values; character group.
